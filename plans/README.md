## Recommended execution order

1. **001, 003, 005** first — highest leverage, each fixes one root cause in many places or on the busiest page (WhatsApp). Independent of each other, safe to run in parallel.
2. **002 before 004** — 002 explicitly skips the two `Layout.tsx` occurrences that 004 owns; running 002 first makes 004's later `grep` cleaner (fewer stray `transition-all` matches to filter past). Not a hard dependency, just less noise.
3. **006, 007, 008, 009, 011** — independent MEDIUM items, any order.
4. **010 before 012** — plan 012's step 4 explicitly coordinates with plan 010's new `pb-lead-alert-out` keyframe (extends the same reduced-motion block). Apply 010 first, or if 012 runs first, revisit its step 4 once 010 lands.
5. **013 last** — a grab-bag of independent one-liners; safe to run anytime, lowest risk, lowest payoff per item.

## Dependencies

- 002 ↔ 004: same file (`Layout.tsx`), disjoint line ranges — no functional dependency, just sequencing to reduce grep noise (see above).
- 010 → 012: 012's item 4 (LeadAlerts reduced-motion) assumes 010's new exit keyframe exists if both are applied — see plan 012's Step 4 note.
- All other plans are fully independent and can be executed and reviewed in any order or in parallel (isolated worktrees).
